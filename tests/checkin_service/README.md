# Automatic foreground check-in scheduling contract

This offline test compiles the actual CheckInService and supplies synthetic Android framework, Store and API adapters. It does not execute real Android JobScheduler or NgaApi HTTP, and never makes a real check-in request. The observable API attempts and their immutable synthetic account/host/cookie values are asserted independently of the coalescer implementation.

The original thirteen scenarios cover 65 pending same-session triggers, future foreground attempts after failure, account/host/cookie switches, keeping only the latest requested scope, returning to the original scope, queued requests before execution, rejecting an unrequested new session, disabling/re-enabling, 257 concurrent triggers, and account/host/cookie switches forced between the Service check and API entry. The immutable expected session must be passed into the API so an unrequested new session cannot inherit the old task. In-flight fake writes must never be interrupted. The actual generic executor queue is inspected to verify no extra task backlog while one is running and at most one queued foreground task before execution; no coalescer fields are inspected.

Run `bash tests/checkin_service/run.sh`. A cached JDK 17 is required; no Android SDK, network or downloaded dependency is needed. The JVM-only `--add-opens` option permits read-only inspection of the standard ExecutorService wrapper; it is not a product runtime option. These sources are excluded from the product APK.

Confirmed-day cases retain OS scheduling while proving zero new credential captures/login resolution and zero HTTP, including a queued task completed before drain and a completion appearing between drain and perform. Next-day requests, account changes and same-account token renewal keep their existing eligibility. A deterministic clock rollover during the saved-day read verifies that the current day is evaluated afterward. A switch after an already-completed account observation may skip only that observation; the new account’s independent explicit trigger remains eligible. These store/clock boundaries are synthetic. The actual LoginPreferences regression separately proves that failed writes and failed rollback preserve the previous account’s confirmed day, and successful account changes/logout clear it.
