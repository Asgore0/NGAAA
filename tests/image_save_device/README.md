# Isolated real MainActivity image-save verification

This helper runs the exact production MainActivity in a separate application UID with no INTERNET permission. It generates a valid 1024×1024 BMP in memory and delivers a synthetic successful request-702 result to the actual Main.onActivityResult method. Its non-exported local ContentProvider returns a pipe; the receiver consumes one block, pauses, then hashes all received bytes in memory. No real user file or remote provider is accessed.

While that real save is blocked, the helper calls Activity.recreate and waits for the old Main to be destroyed and its replacement to resume. It records the old Activity executor's shutdown, the provider-open thread's actual interrupt state and the final byte count/SHA256 match. The baseline observation mode intentionally does not require data loss: classic FileOutputStream may continue despite interruption. Its observations must be reported as measured.

Normal verification requires the final original bytes to survive recreation, then exercises the actual NativeImageSaves API with one active blocked save plus two queued saves. A fourth save must reject promptly, never open a provider on the caller thread and never retry itself; all three accepted writes must eventually match the original bytes exactly. The single-worker/two-pending bound is checked against the production executor. The provider receiver is a daemon and all synthetic gates release in cleanup.

Normal verification additionally opens actual image pages A and B and invokes the actual Main.prepareImageExport method. Both original reads wait on scripted fake HTTP streams, while previews decode a generated valid BMP. Navigating A→B must cancel A; A then returns a controlled late error while B is still preparing. The late A callback must leave B's flag and disabled save button intact. Leaving B must cancel its read and remove preparation/view state. An ACTION_CREATE_DOCUMENT monitor blocks any unexpected picker dispatch and the expected hit count is zero. These read-only scenarios never choose a file or submit a write.

```sh
PRODUCT_JAR=/absolute/pinned/classes.jar \
PRODUCT_JAR_SHA256=<reviewed-jar-sha256> \
PRODUCT_APK=/absolute/candidate.apk \
PRODUCT_APK_SHA256=<reviewed-apk-sha256> \
SIGNING_DIR=/absolute/external-signing-directory \
IMAGE_SAVE_BUILD_DIR=/absolute/isolated-helper-output \
bash tests/image_save_device/build.sh
```

The build requires cached API 35, build-tools 35.0.0 and JDK 17. It downloads nothing, accesses no ADB and never implicitly selects a mutable project jar. The emitted class binding records all production class hashes and both APK hashes; copied product classes in the helper jar and JVM Html stub bytecode are rejected. The debug signing key remains external.

Run only on the root task's designated emulator. Component: `cn.ngapure.imagesavefixturev195/cn.ngapure.imagesavefixturev195.ImageSaveProbe`; argument: `syntheticImageSavesOnly=true`; result key: `safe_image_save_report`. For the immutable old candidate, also use `observeBefore=true`; this only observes actual request-702/recreation behavior and skips the new queue API checks. Its `passed` means the observation completed; inspect `observations.recreateExactBytes` for the measured outcome. Normal final-candidate mode tests the full contract. A separate `observePrepareBeforeOnly=true` mode skips request-702/queue checks and observes only the actual original-preparation race against the immutable old candidate. Its observation `prepareBLateAFailurePreservesPreparing` records the measured result without imposing the fixed behavior on the old baseline. If old navigation retains the preparation flag, the baseline records `prepareNavigationToBResetsPreparing=false`, then explicitly resets this one fixture flag solely to isolate the separate late-callback defect (`baselineFixtureResetRequiredToIsolateLateCallback=true`). The final-candidate test never applies that fixture reset and must pass both contracts naturally.

The helper disables only its own automatic check-in, motion/glass preferences and notifications. It does not start the installed client or access/change that client's account/settings. All startup network attempts fail in a scripted URL handler without a socket. Uninstall the helper afterward. Test classes, generated bytes and the signing key are excluded from the product APK.
