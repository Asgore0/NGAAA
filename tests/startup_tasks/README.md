# Startup local-maintenance deferral

`CheckInService.checkOnOpenAsync(Context)` and `NativeNotifications.onForegroundAsync(Context)` are startup-only wrappers. They capture the application context, then enqueue existing behavior on independent local-maintenance workers; they never wait behind the services' HTTP executors. Check-in calls `checkOnOpen` exactly once (including its scheduler call). When auto-check-in is disabled it still cancels the scheduled job, then returns without capturing credentials or queuing HTTP. A previously queued check also rechecks opt-in before reading credentials. Notifications schedule first, then run foreground polling only when scheduling finds an enabled, permitted, logged-in session. Existing synchronous APIs retain immediate cleanup for explicit logout, opt-out and settings changes.

Notification opt-out or unavailable OS permission invalidates the worker generation and clears the active in-memory/persisted owner projection, cancels the job and notice, and returns without reading credentials. Per-account unread baselines remain intact. The same cleanup runs for a stale scheduled job. Cheap cancellation/settings/generation checks precede the exact-session guard, so disabled, canceled and invalidated workers cannot trigger decryption merely through eager Java argument evaluation. Enabled current work retains fresh exact-session validation before each read and before baseline/notification publication. Disable→reenable and permission revoke→regrant still reject an older in-flight result.

`StartupTaskQueue` has one running task plus one latest pending trigger, with a bounded single-thread executor. Submissions hold only a short metadata lock; scheduler, preference and credential work runs outside it. Foreground bursts replace pending work, not the active task. Runtime failures/rejected submissions release ownership so a later trigger can retry. The queue owns application contexts only; activity navigation, page errors and destruction do not cancel maintenance. Credentials are read when the local-maintenance task runs, and the existing service then passes its exact immutable session to its existing network guard. It never reinterprets an already-captured old network task as a new account. Both services expose numeric `startupDiagnostics()` (counts, pending state and task duration), with no account, cookie or payload strings.

Run `TEST_WORK_DIR=/absolute/fresh/directory bash tests/startup_tasks/run.sh`. It compiles the real queue and both real services; Android platform/preferences/scheduler, current-session storage and transport boundaries are synthetic. `StartupTasksTest` checks bounded latest-trigger work, nonblocking submissions while preference work is stalled, failure/rejection recovery, application-context lifetime, independent progress while HTTP workers are blocked, exact-session rejection after account change, disabled cleanup with zero credential reads/HTTP, and re-enabling after a skipped queued check. `NotificationFastPathTest` exercises real notification control flow with disabled/permission-denied/already-canceled entry points, plus an in-flight synthetic response followed by disable→reenable, permission revoke→regrant, cancellation, account/host/cookie change. Old results cannot start the second endpoint or commit a baseline; the following fresh authorized poll succeeds. These JVM tests do not execute Android Keystore or prove device latency. Existing `tests/checkin_service`, `tests/api/checkin` and `tests/notifications` remain separate regressions for HTTP ownership, account-race and notification behavior.

For already-confirmed check-in days, the real service still reconciles the periodic schedule but skips credential capture and HTTP at entry, queued drain and background-job execution. The saved authoritative day is read before the current date. The wrapper tests stall that preference read with a latch and verify UI triggers remain nonblocking, coalescing and scheduler calls remain intact, a queued completion adds no recapture, and next-day/new-account triggers still reach the exact-session API guard. No pending OPEN_LOCK state is reset by the fast path.
