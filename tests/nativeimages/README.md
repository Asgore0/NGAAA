# Inline image request concurrency

Run `bash tests/nativeimages/run.sh`. The suite compiles the production `NativeImages`, avatar metadata dependencies and cancellation code against lightweight Android fixtures. A fake HTTPS URL handler returns only in-memory bytes: no network, emulator, account, cookies or stored data are used. The verified local test JSON dependency and Android SDK 35 are required; the script downloads nothing.

The 22 shared-loader scenarios reproduce a dense post with 30 copies of one image, then verify one shared fetch and all 30 deliveries. They also cover independent animated drawable instances, cancellation by one subscriber versus the last subscriber, subscribers joining during transport or decoding, queued-delivery cancellation and owner closure, full/inline decode-key separation, 24 unique jobs / 32 globally pending subscribers, recovery after temporary saturation and a permanent HTTP failure. Cache management checks use actual temporary files with controlled decoder fixtures: reported encoded-file bytes, LRU eviction without recycling a displayed bitmap, clearing during media or avatar downloads, a queued task starting after clear, and another loader clearing the shared directory. The fake transport rejects any Cookie or Authorization header.

The fixture decoder models bitmap identity and independent mutable drawable identity. It does **not** verify Android image codecs, animation scheduling, text layout or device rendering. Those remain device checks. Each animated view owns its actual decoder instance; the optional application-private disk cache stores verified original response bytes within 32 MiB / 128 entries / 7 days; no encoded bytes are retained in an additional heap cache. The worker drops its response reference when the shared group finishes. Android drawables may retain decoder-owned resources. Only static bitmaps enter the existing bounded image cache.

The second suite uses real temporary files to verify original-byte round trips, reopened-cache reads, hashed filenames without request metadata, entry/byte LRU limits, expiry and malformed payload rejection, unavailable storage, interruption, concurrent atomic replacement, and nonblocking scrolling metadata. It also verifies selective size/count reporting and clearing, preserving unrelated files and nested directories, rejecting a linked cache root or entry, shared-owner invalidation, and preventing old writes or corrupt-decode cleanup from modifying a new generation. A real temporary directory is made read-only and restored in `finally` to verify failed-deletion counts, actual remaining bytes and a successful later retry. It does not infer heap usage from file sizes.

`NativeImages.cacheStats()` and `clearCaches()` are worker-only APIs. Memory bytes are the loader LRU's accounting, not total process or displayed-image memory. Disk bytes include this cache's regular encoded and pending files (including their headers), not the entire application storage. Clearing removes only those disposable files and drops LRU references; it never recycles a bitmap retained by a view. Existing downloads may still complete for visible views, but their old generation cannot repopulate cleared caches. New work can cache again. A failed deletion is reported with the actual remaining snapshot; a linked/unavailable cache root is reported as inaccessible. No credentials, drafts, local collections or submission journals are opened by these APIs.

The original-byte transport suite binds real production reads to a `RequestCancellation.Token` and uses fake sockets that ignore interruption until disconnected. It covers cancellation before connection, during headers, during `getInputStream`, during body reads and after headers, plus successful registration cleanup. It performs no actual socket or account I/O.

The source-geometry suite covers eight fixture paths (four image geometries in mocked API 27 and 35 routing), independent original and sampled sizes, small images, odd dimensions, bitmap cache wrappers, defensive-copy results and disk-based re-decode. Android dimensions/decoders in this suite are controlled fixtures; `tests/media_device` checks the actual Android ImageDecoder and BitmapFactory implementations, including EXIF orientation. The production logical geometry uses weak image keys with integer-only values; it adds no strong image retention.

The animation backpressure suite holds the main callback queue, verifies that only one independent animation is decoded ahead of it, then delivers all 30 subscribers from one fetch. Eight additional boundaries cover cancellation of the queued subscriber, cancellation of the whole group, closure during the acknowledgement wait, two simultaneous groups, unchanged static bitmap and static non-bitmap paths, a late subscriber, and decoder failure after the first acknowledgement. These are worker/queue checks with controlled decoder fixtures, not Android native heap measurements.

JPEG rotation and mirror transforms are verified by the separate Android helper with EXIF orientations 2–8 and actual image corner pixels. Its checks include shared bitmap cache identity, preservation of a still-displayed bitmap after cache trim and local re-decode, original logical geometry and identical original export bytes. The JVM fixtures are non-JPEG; their `Bitmap.createBitmap` stub deliberately throws if invoked. Passing the JVM suites therefore does not certify EXIF transforms or an Android 26/27 runtime. The full Android helper uses a separate UID, synthetic media and no INTERNET permission.

The cache-admission suite uses an access-order, byte-accounted `LruCache` fixture that really evicts entries, including Android's behavior when a single insertion exceeds the entire budget. Through the production loader's BitmapFactory and ImageDecoder routes it warms avatar/inline pixels, loads an oversized full image, and verifies that returning reuses the same pixels with no additional synthetic transport. Fitting full images still cache; oversized images remain valid for display but are not retained; cached callback cancellation and display-safe trim remain covered. Boundaries include null/recycled/zero allocations, an allocation larger than its logical dimensions, and exactly the cache budget. The `work/native-v208-performance/image-cache-probe` helper separately verifies both full-image routes against real Android codecs and `android.util.LruCache`, using an immutable complete production JAR/APK, separate UID, in-memory synthetic HTTPS and no INTERNET permission. It waits for shared tasks to exit before testing completed-cache reuse.

The single-array payload suite checks the actual reader with short reads, exact 1-byte/16-KiB/20-MiB bounds, early EOF, an added byte after the size snapshot, zero progress, and interruption before reading, during a chunk, and during the final EOF check. Every chunk must target the returned array itself, proving the removed result copy without estimating memory from image dimensions. Existing filesystem and generation tests still run. `work/native-v208-performance/image-allocation/run.sh` additionally records JVM per-thread allocations during real temporary-file reads; those numbers are not Android native heap, RSS or UI frame measurements.
